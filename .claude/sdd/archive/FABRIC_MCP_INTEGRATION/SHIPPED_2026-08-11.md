## Summary

Added a second, parallel "assistant" to the GEFIN Agent: a Fabric — Pipeline de Vendas domain that answers natural-language questions about a real Microsoft Fabric/Power BI semantic model (Sales & Marketing Sample dataset) via a remote MCP server, with the same governance guarantees the existing Contas a Receber assistant already had — catalog-first grounding, generated charts, and per-answer lineage. The user selects which assistant to talk to at the start of a new chat, exactly like switching plugins; each domain loads only its own toolset. The integration was built and verified live end-to-end against the real MCP server, real Postgres database, and a real LLM — not simulated — which surfaced and fixed 5 concrete defects (including a missing tool wiring that would have silently broken chart generation) that static review alone would not have caught.

## Lessons Learned

### Process

- Running the full Brainstorm → Define → Design → Build cycle in one continuous session, with real live testing baked into Build (not deferred), caught defects — a missing tool binding, a dependency conflict, a double-encoding bug — that would otherwise have shipped silently and only surfaced in the user's own hands later. **Treat "Run Full Validation" in the Build skill as license to actually run the system against real external dependencies when the feature's core risk is integration, not just unit-level correctness.**
- The Design phase's dependency compatibility check (reading `Requires-Dist` metadata) was necessary but not sufficient — it missed a transitive `langsmith` conflict that only a real `pip install` surfaced. **For any dependency bump touching a package with a deep transitive tree (LangChain ecosystem, in particular), do a real trial install before finalizing a version pin in DESIGN, not just a metadata read.**

### Technical

- A DESIGN document's code pattern can silently omit something the DESIGN's own prose (Components table, DEFINE goals) already promised — `generate_chart` was described as reused by the Fabric domain in two places, but the literal `tools = [*mcp_tools, *FABRIC_LOCAL_TOOLS]` snippet never included it. **When a code pattern in DESIGN lists an explicit tool/import set, cross-check it line-by-line against every other place in the same document that describes expected capabilities — don't assume prose and code agree.**
- MCP tools converted via `langchain-mcp-adapters` are coroutine-only and return their content as a raw JSON *string* when invoked with a plain args dict (not a full `ToolCall`) — this is a real, non-obvious difference from the codebase's existing hand-written tools, which return native Python dicts. Both the double-encoding bug and the missing-`data`-extraction bug traced back to this one behavioral difference. **When mixing hand-written and adapter-converted tools in the same dispatch loop, explicitly test what each actually returns — don't assume symmetry.**
- An exception handler that returns early on ANY loop iteration's failure — even the very last one, after all the real work already succeeded — silently discards that work. This bug predated this feature but only became consequential once a domain needed enough sequential LLM turns for a late-turn transient failure to be likely. **Any bounded retry/step loop that accumulates partial results should thread those results through every exit path, including the error path — not just the happy path.**

### Communication

- The user provided a real, live MCP server and a working example client script up front, which turned three of the Brainstorm's discovery questions from guesswork into verified fact (the actual tool surface, the actual schema, the actual DAX permission boundary). **When the user can hand over a live, working reference — a script, a running service, a real credential — use it immediately during Brainstorm rather than treating the feature as purely hypothetical; it collapses multiple rounds of assumption-then-correction into one round of direct observation.**

### Tools & Libraries

- `langchain-mcp-adapters` (`load_mcp_tools(session)`) eliminated the need to hand-write LangChain tool wrappers/schemas for the 3 remote MCP tools, exactly as hoped in the Brainstorm's Approach A — but its dependency footprint (`langchain-core>=0.3.36`) was the source of the one real dependency conflict in this build. **The convenience of an adapter library is a real trade-off against the version-pinning discipline of an already-mature `requirements.txt` — worth the trade here, but budget time for it explicitly next time.**
- Running the actual Docker image (not just a local venv) for verification caught nothing extra this time (the venv and the container behaved identically), but was cheap insurance given the feature's production deploy target is that same image — **worth keeping as a standard Build-phase step for any feature touching `backend/requirements.txt`.**

## Recommendations for Future Work

| Area | Recommendation |
|------|------------------|
| LLM provider verification | Re-run the chart-generation acceptance test with `LLM_PROVIDER=anthropic` once a valid `ANTHROPIC_API_KEY` is rotated in — the currently saved key returns 401. The project's own docs already recommend Claude for tool-calling quality; this build's evidence (gpt-4o-mini needing 60-110s+ and occasionally timing out on the same request) reinforces that recommendation specifically for the Fabric domain's longer multi-turn flows. |
| Frontend visual verification | The domain selector was verified by code review and a container boot check, but never clicked through in a real browser (no browser automation tool was available this session). Do a manual pass in a browser before treating the UI as fully verified. |
| Lineage precision | `get_fabric_lineage`'s report-page mapping is an explicitly-labeled heuristic (the MCP server exposes no real measure→visual binding). If a future Fabric integration adds a metadata API that does expose this, replace the heuristic mapping in `catalog/fabric_metrics.yaml` rather than layering more guesswork on top. |
| Roadmap item already flagged in DEFINE | End-to-end (Purview-style) lineage was explicitly out of scope for this MVP; still tracked as a future direction if the portfolio narrative wants a deeper governance story. |
| PII review | `Contacts` and other unexplored table columns were flagged as a risk (A-004 in DEFINE) but never fully audited column-by-column, since the catalog only exposes measures (not raw table columns) to the LLM — low risk today, but worth a explicit pass before this catalog is ever extended to expose dimension columns directly. |
