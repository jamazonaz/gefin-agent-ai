## Summary

O GEFIN Agent saiu do ambiente puramente local (`docker-compose`) e passou a rodar em produção real, usando apenas serviços com tier gratuito permanente: backend FastAPI no Render (Docker Web Service), banco PostgreSQL no Neon (serverless) e frontend Streamlit no Streamlit Community Cloud. O valor de negócio entregue é acesso público — qualquer stakeholder pode abrir uma URL e conversar com o agente sobre Contas a Receber sem precisar clonar o repositório ou rodar Docker localmente. Além do deploy em si, a execução real revelou e corrigiu 9 problemas de produção (builds quebrados, timeout ausente em chamadas de LLM, falta de guardrail de escopo, e inconsistências de dados entre views) que não teriam aparecido só com testes locais.

## Lessons Learned

### Process

- Tratar o deploy real como continuação direta do ciclo SDD (em vez de considerar o Build "pronto" assim que o código compila) foi o que revelou os 9 problemas reais — testes locais nunca teriam pego build hang no Python 3.14 do Streamlit Cloud, nem a latência real de chamadas de LLM contra a API de produção.
- Usar `git status`/diff review antes de cada commit (em vez de `git add -A` cego) evitou commitar arquivos de teste temporários (`test_app.py`, `test_app_build.py`) criados durante verificação.

### Technical

- **Ambientes diferentes = versões de dependência diferentes.** O mesmo `requirements.txt` não serve para Docker local (Python 3.12) e Streamlit Community Cloud (Python 3.14) quando há pacotes com extensões compiladas (`numpy`/`pandas`/`pyarrow`). A solução foi separar o pin em um `constraints-docker.txt` aplicado só no build Docker, deixando a plataforma cloud resolver livremente.
- **SDKs de LLM têm timeouts default de vários minutos.** Sem configurar `timeout` explicitamente em `ChatAnthropic`/`ChatOpenAI`, uma chamada lenta trava até o proxy da plataforma cortar a conexão, sem nunca cair no `except` da aplicação. O valor certo do timeout não deve ser adivinhado — foi calibrado medindo a latência real (fluxo de 6 passos com dataset de 90 dias leva genuinamente 50-100s no OpenAI).
- **Guardrails de prompt sozinhos são frágeis.** Uma instrução em texto livre no system prompt depende do modelo "decidir" obedecer. Forçar uma tool call com `tool_choice` e schema estruturado (`triage_scope`) é mais robusto porque não há canal de texto livre para o modelo escapar da regra — mas precisa de escopo bem definido, incluindo casos de borda como perguntas meta sobre o próprio sistema (achado só depois, com uso real).
- **Views agregadas em formatos diferentes (série temporal vs. uma linha por entidade) são uma armadilha de agregação.** `SUM()` ingênuo sobre uma view de série temporal (`vw_ar_kpi_daily`) produziu um valor 86x maior que o correto. A correção não foi no SQL da view (que estava certo para seu propósito), foi documentar a semântica no catálogo para guiar o agente.

### Communication

- Pedir para o usuário colar logs reais (Render dashboard, Streamlit Cloud "Manage app") em vez de tentar adivinhar a causa a partir só da mensagem de erro genérica economizou várias rodadas de investigação às cegas — funcionou bem tanto para os erros de infraestrutura quanto para os de dados.
- Quando o usuário perguntou "isso pode ser feito através de contratos?", a resposta mais honesta foi diferenciar "contrato de saída estruturada" de "data contract" antes de implementar — evitou construir a coisa errada.

### Tools & Libraries

- `streamlit.testing.v1.AppTest` permitiu rodar o fluxo real do frontend (incluindo o bug de ordem de `st.set_page_config()`) sem precisar de navegador — pego numa fase muito mais barata do que só descobrir em produção.
- `gh api` para branch protection resolveu um impasse real: o GitHub não deixa o autor aprovar a própria PR, então `required_approving_review_count: 1` trava um projeto solo. `required_approving_review_count: 0` (com `enforce_admins: true`) mantém push direto bloqueado sem esse impasse.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Cold start (AT-002) | Fazer um teste dedicado aguardando os 15 min de inatividade do Render, para confirmar a experiência real do usuário durante o spin-up (~1min) — não testado explicitamente nesta feature |
| CI/CD | Fora de escopo aqui por decisão explícita do Define; considerar ao menos um lint/syntax-check automatizado em PR antes de mesclar, já que vários dos 9 problemas pós-deploy eram detectáveis estaticamente (ex.: pin de dependência sem wheel disponível) |
| Guardrail de escopo | Monitorar por mais falsos positivos (o padrão "pergunta meta sobre o sistema" já apareceu uma vez); considerar logar decisões `triage_scope` para revisão periódica |
| Observabilidade | Fora de escopo no Define; conforme o uso cresce, os logs nativos do Render/Streamlit Cloud podem não ser suficientes para investigar problemas de latência de LLM como o encontrado nesta feature |
